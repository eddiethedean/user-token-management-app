## Description

The real Databricks writer rejects a valid timestamp schema generated by the CSV connector before issuing CREATE TABLE. The mapping recognizes a shortened handwritten Polars dtype string but not the actual parameterized string produced by Polars.

## Expected Behavior

A supported CSV timestamp column maps to an appropriate Delta timestamp declaration and can be staged. Timezone-aware variants must preserve the intended instant semantics.

## Actual Behavior

CSV inspection produces `Datetime(time_unit='us', time_zone=None)`. Calling the real writer with that schema raises `UNSUPPORTED_TYPE`; no staging CREATE TABLE is emitted. The SQL/management boundaries use the repository harness, not a live workspace.

## Root Cause Analysis

`_sql_type` matches only the literal `datetime(time_unit='us')`. `CsvSourceConnector.inspect_object` uses the complete Polars type representation with `time_zone=None`; UTC-aware representations are also absent from the mapping. This writer-side failure is independent of the engine normalization bug: CSV inspection and extraction agree with each other, but staging rejects their common type.

## Impact

CSV timestamp routes to Databricks fail even though the source is supported and can be parsed. Equivalent parameterized dtype schemas from Parquet sources reach this same mapping. No destination publication occurs in the reproduced failure.

## Suggested Fix

Map structured/normalized Datetime variants rather than one literal string. Define timezone-aware and naive mappings explicitly, then use the same mapping for declarations and append compatibility.

## Test Coverage Gaps

Existing type mapping tests and harness schemas use shortened hardcoded timestamp strings. Feed schemas from actual CSV/Parquet inspection into real Databricks prepare/create and append checks; cover naive and UTC-aware variants.
